# 讨论·输入条口径（tester 一份）

议题：频道页/聊天页那片输入区到底「不该出现的场景就不保留（A）」还是「保留但必须真能用、能指定发给频道里某个角色（B）」。
同一片输入区的三个症状：R-41（回车不能确认/发送）、R-42（频道页点开不能聊天）、R-44（给 tmux 用的那条输入条）。
测试者角度＝**只看"能不能验、凭什么说合格"**。

## 1. 候选 A（不该出现的场景就不保留输入条）的代价与风险
- **判据好写、但"该不该出现"的清单不定死就没法判**：A 案的合格线是"该出现的场景出现、不该出现的场景不出现"。
  场景清单（哪块板块、什么状态该有输入条）不由测试者定 ⇒ 清单没定时我只能记**读数**、判不了**合格**，
  最终会出现"两边都说自己对"（R-33/R-35 的"遮挡/间距"就是这么过来的）。
- **最大风险：把本人真正要的东西一起收走**。本人原话是「我可以使用它，把这段话发送给频道里的某个角色」——
  A 案如果只做"隐藏/收走"，频道页就**只能看不能发**，等于用一个缺陷换另一个缺陷。
- **代价**：A 案没有正向用例（只能验"没出现"），而回归面反而更大（8 个板块 × 出现条件）。
  真机验法只能是"逐板块看有没有多出控件"＋"该出现的板块点一下没反应就不算过"。

## 2. 候选 B（保留，但必须真能用、能指定收件人）的代价与风险
- **这是唯一可被真机复核的方向**：能点、能数、能对账 —— 一条消息发出去后，「收件人是不是我选的那个」有四个独立读数：
  ① RPC 的 `talk.say{role}` 参数原文；② 平台台账 `talk.db.delivery(msg_id,role,ok,ms)`；③ 对方会话条数 +1（`~/.hermes/state.db.messages` 按 session_id 数）；
  ④ 界面上的气泡/状态行。四个都对上才叫"发给了对的人"。
- **风险 a（最要紧）：指定了收件人却发给了别人**。输入条如果不**常显**当前收件人，用户以为发给 A、实际沿用上次的 B ——
  这是"隐藏状态"型缺陷，比"发不出去"更难发现。判据：UI 必须可见收件人（文案里带名字/全体），
  且**不允许无收件人发射**；验法：选 A 发一条 → 台账只应出现 A、A 的会话 +1、B 的会话**不变**。
- **风险 b：默认收件人歧义**（频道页默认"全体"还是"某角色"）。判据：默认值必须有明确文案；测试时"默认态"要单独点一次。
- **风险 c：同一片输入区的两种语义不能串**（正是 R-41/R-44 的现场）：
  "发消息"框的 Enter 只能触发发送（`talk.say`/`talk.answer` 各 1 次）；"给 tmux 用"的输入条 Enter 只能触发终端 `send`。
  判据：两条路分别记 **事件序列 + RPC 次数**（keydown/keyup/beforeinput 有没有、keyCode 多少），
  且同一次回车**只准发 1 条**（现有 400ms 闸口径）。**串了就是红**——例如一个 Enter 把聊天内容塞进别人终端。
- **风险 d：三处输入框共用一套逻辑 ⇒ 一处错三处错**（R-41 的 `bindEnterSend` 就是单聊/群聊/授权框共用）。
  判据：三处**各自**真机点一遍（分板块口径），不能只验一处就放行。
- **代价**：比 A 大（要带状态：收件人、模式、可见性），但可验证面最大，也是唯一对得上本人诉求的方向。

## 3. 证据（可复核）
1. `evidence/R41-定位-20260925/`（作者 #1315：三个输入框的回车现状与改法）；`evidence/R41-实现与出包-20260925/`（渲染者 #1320：
   `enterkeyhint=send` + keydown 主路 + keyup(13)/beforeinput 兜底 + 400ms 闸 + Shift+Enter 不发 + 组字中不发）。
2. **本机真机复测实测（R41-3，报告未交，读数已在 `evidence/R41-复测-20260925/回车发送-原始输出.json`）**：
   在单聊 `#tk-sayin` 真焦点 + 真按键（`adb shell input keyevent 66`）后，输入框收到完整序列
   `keydown(Enter, keyCode 13)` → `beforeinput(insertLineBreak)` → `keyup(Enter, 13)`，
   但 **`talk.say` 调用 0 次、气泡 0 个、文字仍留在框里**（真机、真按键事件，不是合成事件注入）
   ⇒ "输入条在，但回车不通"的现场。**这一条同时也说明：B 案的判据必须先能测出"到底有没有发"。**
3. `evidence/R38-复测-20260924/结论-R38-复测.txt`（底部固定层 vs 列表末条：滚到底后 0 重叠、间隙 24px）；
   `evidence/R32-复测-20260924/结论-R32-复测.txt`（单聊输入条 `#tk-sayline` sticky 压住列表末条 56px；同页**两套** `tk-sayin` 输入框、重复 id）。
   → 这片输入区的历史账：它既可能"盖住内容"，也可能"有两份"，验的时候必须点名是哪一份。
4. 台账口径（复核用）：`roles-chat/talk.db` 的 `delivery`（`msg_id,role,ok,ms`）＋ `talk.py deliveries`；
   `~/.hermes/state.db` 的 `messages`（按 `session_id` 数条数，判"对方 +1"）。

## 4. 我投哪一票
**B**。一句话理由：只有 B 能定出**可复核的判据**（真机点 + 台账证明"收件人真是我选的那个"、对方条数 +1），
A 案只能验"没出现"，验不了本人那句"我可以使用它"。
（若最终选 A，请把"该出现场景清单"先写进规范，否则测试者只能给读数、给不出合格判定。）
