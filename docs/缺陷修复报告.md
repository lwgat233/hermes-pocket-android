## 缺陷 1 — 随便按哪个地方都弹键盘

**复现**：单击终端区域，`document.activeElement` 变成 xterm 的隐藏输入框 → 软键盘弹出，盖掉半屏。

**根因**：`app.js` 的手势处理里，单击（非 TUI 鼠标模式）无条件执行 `this.term.focus()`。

**修复**
- 单击终端**默认不抢焦点**（`tapKeyboard` 默认为 false）
- 功能键条新增两个显式按钮：**「⌨ 键盘」**（开/收终端键盘）、**「✎ 输入」**（打开输入框，长文本/中文更顺手）
- 长按菜单里也加了「⌨ 打开/收起键盘」
- 想改回「点一下即弹」，设置里有开关「点击终端弹出键盘」

**验证**：单击后 `activeElement=BODY`（不抢焦点）；「⌨ 键盘」能打开、再按能收起。

## 缺陷 2 — 密钥无法生成

这条是三层问题叠在一起，前两层修完第三层才露出来。

**复现**：点「生成」→ 立刻（约 8ms）报 `java.lang.UnsupportedOperationException`。ECDSA 却成功，说明只有 EdDSA 这条路径坏。

**根因 1：Android 的 ART 不做多版本 JAR 查找**
jsch 把 EdDSA 的真实实现放在 jar 的 `META-INF/versions/15/` 下，顶层留的是「要求 Java15+」的**桩类**：

```
public KeyPairGenEdDSA() { throw new UnsupportedOperationException("KeyPairGenEdDSA requires Java15+."); }
```

桩类**存在且能加载**，所以 jsch 认为该算法可用，永远不会退回 BouncyCastle 实现。同一根因还有另一个表现：`ssh-ed25519` 会静默从 `server_host_key` 提案里消失（上一轮已修）。

**修复 1**：启动时显式覆盖四个配置键（`JSch.setConfig` 是全局静态的，没有实例级配置）：
```kotlin
JSch.setConfig("keypairgen.eddsa", "com.jcraft.jsch.bc.KeyPairGenEdDSA")
JSch.setConfig("keypairgen_fromprivate.eddsa", "com.jcraft.jsch.bc.KeyPairGenEdDSA")
JSch.setConfig("signature.ed25519", "com.jcraft.jsch.bc.SignatureEd25519")
JSch.setConfig("signature.ed448", "com.jcraft.jsch.bc.SignatureEd448")
```

**根因 2：jsch 上游根本不支持用旧 PEM 导出 EdDSA 私钥**
修完根因 1 后生成仍然失败。查 jsch 源码，`KeyPairEdDSA` 里写着：

```java
/* XXX: SSH_OPENSSH_V1 isn't supported yet, have these methods fail. */
@Override byte[] getBegin() { throw new UnsupportedOperationException(); }
@Override byte[] getEnd()   { throw new UnsupportedOperationException(); }
@Override byte[] getPrivateKey() { throw new UnsupportedOperationException(); }
```

`KeyPairEd25519` 没有覆写这三个方法（RSA 的类则有），而 `vendor` 字段是包私有的、没有公开 setter，`VENDOR_OPENSSH_V1` 常量也拿不到。Android 上又没有 `ssh-keygen` 可以调。

**修复 2**：用 BouncyCastle 生成密钥，并按 `openssh-key-v1` 布局自己拼私钥（约 60 行）。
附带好处：需要口令时，把这个 v1 PEM 交给 jsch 读回来再写一遍 —— jsch 解析 v1 后内部 vendor 变成 `VENDOR_OPENSSH_V1`，此时 `writePrivateKey(口令)` 才走 v1 分支（bcrypt 加密）。

**验证（这一层用了三重证据）**
| 证据 | 结果 |
|---|---|
| 三种算法生成并读回 | ed25519 38ms / 419 字节；ecdsa 15ms / 227 字节；rsa **1778ms** / 3243 字节 |
| `ssh-keygen -y -f` 从 App 生成的 PEM 派生公钥 | 退出码 0，派生结果与 App 报告的**完全一致** |
| `ssh-keygen -lf` 指纹 | `256 SHA256:zClfJ1Vw… (ED25519)`，与 App 计算一致，注释也读对了 |
| **宿主真 `ssh` 用这把密钥登录** | `AUTH_OK_with_app_generated_key` / `lwgat` |
| **应用内用同一把密钥连接** | `state=connected`，终端回显 `APP_AUTH_OK_lwgat` |

## 缺陷 3 — 输入后被过快刷新掉，要点击确定

**复现**：两处都能重现。

**根因 A：发送把草稿吞了**
`sendComposer()` 无条件 `ta.value = ''`。未连接时点「发送」，只是弹个提示，**但输入框已经清空了** —— 敲的一长段直接没了。

**根因 B：面板重绘把正在填的表单清掉**
`openPanel()` 无条件调 `Panels.renderAll()`，而 `renderAll()` 用 `innerHTML` 重建页签。

**修复**
- 未连接/传输断开时**保留草稿**并提示「还没连上，草稿已保留」
- `renderAll()` 在「主机表单已打开」「密钥表单已打开」「正在设置页输入」时跳过对应页签的重绘

**验证**：未连接点发送后草稿仍在；手工触发重绘后，表单里已填的「草稿名 / 10.0.0.9」仍在。

## 缺陷 4 — tmux 的滚轮支持

**结论**：之前**没有真正做通**，现在补齐了，并且把「为什么滚不动」也讲清楚了。

**根因**：备用屏在**本地**没有 scrollback（xterm 在 alt 屏不存历史），唯一出路是把滚轮事件发给远端、由 tmux 自己滚。但 tmux 默认不接管鼠标（`mouse off`），而 App 在「无鼠标模式」时**静默什么都不做** —— 表现就是「滑了没反应，像卡了」。

**修复**
- 无鼠标模式滚动时给出**可操作提示**：`tmux set -g mouse on`（5 秒节流，不刷屏）
- 「▤Hermes」快捷菜单新增：**开启 tmux 鼠标 → 支持滚轮/点选**、关闭 tmux 鼠标
- 默认会话命令改为 `tmux new -As hermes 'hermes --tui' \; set -g mouse on`
- 新增「⇞ 回滚」键：发 tmux `prefix + [` 进 copy mode，之后 ↑↓/PgUp 翻历史、q 退出 —— **不依赖鼠标**的回滚通道
- 顺带修正修饰键编码：`Ctrl/Alt + 方向键` 现在用 xterm 标准的 `CSI 1;<mod>` 形式（`Ctrl+↑` → `\x1b[1;5A`），之前是往序列前面逐字符贴 ESC，会产生乱码序列

**验证**（逐条对照期望值逐字节核对）
| 输入 | 结果 |
|---|---|
| `SGR 滚轮上/下` | `\x1b[<64;11;6M` / `\x1b[<65;11;6M` ✓ |
| `X10 滚轮上` | `\x1b[M` + `0x60 0x21 0x21` ✓ |
| `SGR 左键按下/抬起/拖拽` | `\x1b[<0;4;5M` / `…m` / `\x1b[<32;4;5M` ✓ |
| `Ctrl+a / Alt+a / Ctrl+Alt+a` | `0x01` / `ESC a` / `ESC 0x01` ✓ |
| `Ctrl+↑ / Alt+↑ / Ctrl+Alt+↓` | `\x1b[1;5A` / `\x1b[1;3A` / `\x1b[1;7B` ✓ |
| `Ctrl+PgUp` | `\x1b[5;5~` ✓ |
| 无鼠标模式滚动 | 不误发滚轮序列，只弹提示 ✓ |
| tmux `mouse on` 后 | 客户端确实请求了鼠标模式（mode=1002）✓ |

## 额外发现：协议里关联 id 与业务 id 撞名（超出你报告的范围）

修缺陷 2 时撞上的，**是个会让功能彻底哑掉的真 bug**。

`transport.js` 这样组包：
```js
this.send(Object.assign({ t: type, id }, payload || {}));
```
而 `key.reveal` / `key.delete` / `host.delete` 的载荷**自己就带一个 `id`**（业务字段，指密钥/主机 id）。于是请求的关联 id 被业务 id 覆盖 → 原生侧 `m.optLong("id")` 读到的是个字符串 → 得 0 → 判定「这条不是请求」→ **永远不回包**，前端只能等到超时。

更迷惑的是：Kotlin 日志把 `reveal: replied` 打在 `if (hasId)` **外面**，所以日志看着一切正常。而且它是「无声失败」——JS 侧的 `JSON.parse` 失败也会被静默吞掉，连报错都没有。

**修复**：关联字段独立命名 `_rid`，前端 / Kotlin / Node 桥三处同步改（业务字段 `id` 保持不动）。

**验证**：`key.reveal` 恢复到 91ms 返回 411 字节 PEM；`key.delete`、`host.delete` 正常；Node 桥 e2e 加了这条回归后 19/19。

## 缺陷 5 & 6 — 点主机的「连接/删除」没反应、长按弹出的项也没用

这两条是**同一个根因**：弹出的菜单被两个抢跑的处理器提前关掉了。

**复现**：点主机卡片弹出「▶连接 / 编辑 / 复制 ssh 命令 / 删除」，点其中任何一项都没反应；终端长按弹出的 8 项也一样。

**根因**
1. `bindChrome()` 里有一行
   ```js
   document.addEventListener('pointerdown', () => this.hideCtx());
   ```
   触摸/点击的事件顺序是 `pointerdown → pointerup → click`。**pointerdown 就把菜单藏了**，
   等到 click 该落到按钮上时，按钮已经是 `display:none` —— 浏览器在 pointerup 时重新做命中测试，
   只会在手指底下找到终端，于是 click 落到终端上，菜单项的 `fn` 永远不会执行。
2. `#ctxmenu` 是 `#stage` 的子元素，所以点菜单项还会冒泡到下面的**终端手势处理**里，
   被当成「点了一下终端」再执行一次 `hideCtx()`。同一路径还会误发一次鼠标点击给远端。

**修复**
- 手势处理加 `inChrome(target)` 守卫：来自 `#ctxmenu / #overlay / #toast / .hp-dialog` 的事件
  一律不进入终端手势逻辑（down/move/up 三处都加）
- 文档级 `pointerdown` 只在**点在菜单之外**时才收起菜单
- 弹出的确认框 / 明文查看层补上 `.hp-dialog` 标记，纳入同一个守卫

**验证（A/B 对照，用真实输入事件）**
先用「已知能用的控件」校准了测试工具：CDP 的 `Input.dispatchTouchEvent` **只送 pointer 事件、不合成 click**
（对照组：touch 点击 click=0 次、鼠标点击 click=1 次），所以必须用 `Input.synthesizeTapGesture`
或鼠标事件路径 —— 否则测出来的「点不动」是测试工具的假象。

然后把「旧的那一行」用开关插回去做 A/B：

| 条件 | 点菜单项的结果 |
|---|---|
| A：开关 ON（= 修复前那行还在） | 命中 **0** 次，菜单被关掉 ← 就是你看到的「弹出来但点不动」 |
| B：开关 OFF（= 修复后） | 命中 **1** 次，菜单正常关闭 |

真实界面路径也全过：
- 点主机卡片 → 菜单弹出，4 项（▶连接 / 编辑 / 复制 ssh 命令 / 删除）
- 点「编辑」→ 菜单关闭 + 表单打开 + 回填了主机名
- 终端长按 → 长按菜单弹出，8 项
- 点「✎ 打开输入框」→ 输入框出现 + 菜单关闭

## 缺陷 7 — 连接后输入时 Esc 等键位被隐藏

**复现与量测**（先量后改）
功能键条当时是 `overflow-x: auto` 的横滑条：

| 模式 | 内容宽 | 可视宽 | 键数 | 默认可见 |
|---|---|---|---|---|
| shell 行 | 1454px | 393px | 28 | 8 |
| TUI 行 | 1068px | 393px | 20 | 8 |

也就是说 20–28 个键里只有 8 个能看到，Ctrl / ⌫ / ^C 这些根本不在视野里。
更糟的是：**某个右侧键获得焦点时，浏览器会自动把整行滚进视野**（实测 `scrollLeft 0 → 675`），
于是 `Esc Tab ⇧Tab ↑ ↓ ← →` 整排被卷出屏幕左边，而且不会自己滚回来 ——
这就是「输入时 ESC 等键位被隐藏」的现场。

**根因**：键条做成横向滚动条。手机上横滑条既看不全也够不着，还容易被 focus 卷走。

**修复**：改成 **8 列网格铺满、永不横向滚动**
- 主键固定 15 个 + 「⌄更多」= 16 个，正好铺满 8×2 行，**全部可见**
  - shell：`Esc Tab ⇧Tab ↑ ↓ ← → ⌫ Ctrl Alt ^C ^D ⌨键盘 ✎输入 ▤` + `⌄更多`
  - TUI：`Esc Tab ⇧Tab ↑ ↓ ← → ⏎ PgUp PgDn ⇞回滚 ⌫ ^C ⌨键盘 ▤` + `⌄更多`
- 冷门键（F1/F2/Home/End/清屏/粘贴/符号键/空格/^Z/^L）收进「⌄更多」那一行，同样 8 列网格，按模式重建

**验证**

| 检查 | 结果 |
|---|---|
| 主键行是否横向溢出 | 内容 393 / 可视 393 —— **不溢出** |
| 主键是否全部可见 | **16/16**（Esc 打头，⌄更多 收尾） |
| 最右侧键获得焦点后 Esc 是否被卷走 | **没有被卷走，scrollLeft 仍为 0** |
| 「⌄更多」开合 | 展开后 16 键、同样不溢出；能收起 |
| 键盘弹起后键条 | 高 97px，完整落在可视区内；终端仍剩 641px |
| 命中测试（可见行的第一个键） | `elementFromPoint` 正确落在 `Esc` 上 |
| **真实点击** Esc / ⌫ | 发出 `1b` / `7f` |
| **真实点击** Ctrl（latch）→ ^C | latch 生效，发出 `03`，且发出后自动释放 |
| TUI 模式下真实点击 ^C | 发出 `03`，且 Esc 仍在视野内 |

## 缺陷 8 — 键盘弹出时键条不跟随 / 有等待感

**现象**：键盘弹起时键条和输入框不是跟着动画一起上浮，而是"先不动、过一会儿才跳上来"。

**根因**：旧代码只在 composer 的 focus/blur 之后 `setTimeout(..., 250)` 才更新 `--vh`，
键盘动画（约 200–300ms）都快放完了布局才开始动。

**修复**：把「跟着键盘走」和「重排终端」拆开
- `visualViewport` 的 `resize` + `scroll` 每帧都触发，回调里**只改 `--vh`/`--vtop` 两个 CSS 变量**
  （不做任何布局查询），键条当帧就跟着键盘上移 —— 这部分必须零延迟
- 真正昂贵的 `term.resize()` 单独防抖 120ms，等键盘动画停下来再重排一次
  （否则每帧重排终端会卡）

**验证**（同一段测量跑两遍，只换 `syncViewport` 的时机；视口变化 778→460 分 12 步注入，每步 28ms）

| | 最大偏差 \|可视高 - 布局高\| | 不一致帧 | 键盘动→布局跟上 |
|---|---|---|---|
| **修复后** | **0px** | **0/29** | **0ms** |
| 修复前（250ms 延迟） | 80px | 18/30 | 255ms |

键盘弹起后键条本身仍完整落在可视区内（高 97px，底边 == 可视区底边），终端区还剩 590px。

## 缺陷 10 — 每次连接都提示「指纹发生变更」

**现象**：每次连都弹「与已保存的指纹不一致！这可能是中间人攻击」，而且**连接直接被判失败**。

**根因**：`known_hosts` 只按 `host:port` 存**一条**指纹，不区分密钥类型。
真实 SSH 的 known_hosts 是**每种密钥类型各一行**。服务器同时提供 ed25519/ecdsa/rsa 时，
只要这次协商到的类型和存的那条不同，就会误报"变更"。
这台机器必然踩到：`Ssh.kt` 早期版本因为没有 BouncyCastle、jsch 做不了 Ed25519，
协商到的是 **ecdsa**，用户信任的是 ecdsa 指纹；后来补上 BC，现在协商 **ed25519** → 指纹必然不同。

**复现**（给测试 sshd 加上 ecdsa/rsa 主机密钥，把 known_hosts 写成"升级前信任过的 ecdsa"）

```
第 1 次  known=true changed=true algo=ssh-ed25519
        弹窗「与已保存的指纹不一致！这可能是中间人攻击。」→ state=error（连不上）
```

**修复**
1. `known_hosts` 改为**按 (主机, 密钥类型) 分别记录**；旧扁平格式自动迁移（原记录不丢）
2. 判定拆成三种，不再一律当警报：
   | 情况 | 判定 | 表现 |
   |---|---|---|
   | 同类型 + 指纹一致 | 正常 | **完全静默，不弹任何框** |
   | 已知主机 + 另一种密钥类型 | 正常现象 | 平静提示「服务器这次提供的是另一种密钥类型」，可信任并记录 |
   | 同类型 + 指纹不同 | **可疑** | 报警，同时列出**已保存的**和**本次收到的**两个指纹 |
3. 更新指纹后**自动重连**，不再让用户手动再点一次
4. 加「🔑 忘掉本机指纹」逃生口（列出已记录的指纹类型，可清除后重新 TOFU）

**验证**（known_hosts 里放升级前的 ecdsa，服务器协商 ed25519）

```
① 事件 known=true changed=false newType=true
   弹窗「这台主机你以前信任过，但服务器这次提供的是另一种密钥类型：ssh-ed25519」→ state=connected ✓
   记录 → {"keys":{"ecdsa-sha2-nistp256":{...},"ssh-ed25519":{...}}}   ← 旧记录保留 + 新增 ✓
② 再连：弹框 0 次，connected ✓
③ 第三次：弹框 0 次，connected ✓
```

> 顺带修掉一个我这次改动自己引入的漏洞：第一版修复漏了「已知主机 + 同类型 + 指纹一致」这一层，
> 会一路落到「首次连接」分支，于是**每次连接还是白弹一个框**。补上静默分支后才真正干净。

## 缺陷 11 — 终端窗口比屏幕还宽（列数超出屏幕宽度）

**现象**：终端横向超出屏幕，要么左右滑动才能看全，要么为了塞下列数把字缩得很小。

**量测**（393px 宽的竖屏，真 TUI = tmux alt-screen）

| | 列数 | 字号 | 屏幕能容纳 | 渲染宽 | 超出屏幕 |
|---|---|---|---|---|---|
| 修复前 | 80 | 10px | 62 | 480px | **+87px（要横滑）** |
| 修复后 | 48 | 13px | 48 | 374px | −19px（适配） |

**根因**：`Geom.apply` 在 auto 模式 + TUI 下会**强行凑到 80 列**
（`cols = max(d.cols, tuiMinCols=80)`，还为此把字号缩到 10px）。
竖屏手机在可读字号下只有 ~48 列，于是必然宽出屏幕。

**修复**
- **默认按屏幕宽度铺满**：能放多少列就用多少列，一点横向滑动都不需要
- 「为了 TUI 凑 ≥80 列」改成显式开关「TUI 保真」，**默认关闭**
- 真超出屏幕时（手动设了太宽的列数）顶栏显示 `⟷` 记号，不再让人以为是显示坏了
- 「窗口大小」对话框里实时显示**「屏幕在 Npx 字号下可容纳 X 列」**，
  列数填超了就警告「⚠ 超出屏幕 N 列，要左右滑动」，并给一个**「适配屏幕宽度」**一键填好

**顺带修掉两个真 bug**

1. **「恢复自适应」没还原字号**：手动模式设成 9px 后点恢复自适应，列数回来了但字号留在 9px
   （因为 `baseFont` 又去读那个被手动改过的 `fontSize` 偏好）。
   现在进入手动模式时把原字号记进 `fontSizeManualBackup`，恢复时还原。
2. **布尔偏好解析是错的**：`!!this.pref('tuiFidelity', false)` —— 当偏好里存的是**字符串** `"false"`
   时，`!!"false"` === **true**，开关反着来。
   这不是新开关独有的，`showKeybar`/`showComposer`/`tapKeyboard`/`touchMouse`/`longPressMenu`/
   `keepAwake`/`nerdFont` **全都有这个隐患**。统一加了 `HP.truthy()` 稳健解析
   （真布尔 / 字符串 `'true'`/`'false'` / 数字 1/0 都能正确判），设置面板的勾选框渲染也走它。

另外修了一处笔误：`if (cols !== term.rows || rows !== term.rows) term.resize(...)`
（拿列数跟当前行数比），已改为 `cols !== term.cols`。

**验证**

| 检查 | 结果 |
|---|---|
| 普通 shell 下默认几何 | 48×33，字号 13，超出 −19px，无 `⟷` ✓ |
| **真 TUI（tmux alt-screen）下默认几何** | **48×33，字号 13，超出 −19px，pan=false** ✓ |
| 打开「TUI 保真」 | 80×46，字号 10，超出 +87px，顶栏出现 `⟷` ✓ |
| 关掉「TUI 保真」 | 回到 48×33 / 13px / 不超出，记号消失 ✓ |
| 对话框「屏幕可容纳 N 列」 | 「屏幕在 13px 字号下可容纳 48 列」 ✓ |
| 填 200 列时 | 「⚠ 超出屏幕 152 列，要左右滑动」 ✓ |
| 字号联动 | 20px→31 列，10px→62 列（实时变化）✓ |
| 「适配屏幕宽度」 | 自动填入 62（= 该字号下的可容纳列数）✓ |

## 缺陷 12 — 大字号下终端又被撑宽；字号上限太小（双指缩放卡在 24px）

**现象**：想要大字号，但字号一大终端又会横向超出屏幕。

**根因（两处）**

1. `Geom.apply` 里有一句统一的下限夹取
   ```js
   cols = Math.max(20, Math.min(this.hardMaxCols, cols));
   ```
   字号调大后屏幕能放下的列数会变小（40px 字号下只剩 15 列），
   这个「最少 20 列」的夹取会**把它抬到 20 列 —— 抬高多少就等于超出屏幕多少**。
   也就是说上一处修复只解决了默认档位，字号一大问题就复发。
2. 字号上下限散在三处且互相不一致，其中**双指缩放被固定在 7–24px**：
   ```js
   const f = Math.round(Math.max(7, Math.min(24, ...)));   // 放不大
   ```
   设置面板上限 24、对话框上限 32 —— 想要大字根本调不上去。

**修复**
- 分清楚列数是「屏幕算出来的」还是「人为指定的」：
  **屏幕算出来的列数绝不被抬高**（那种情况只夹一个极低的下限 2）；
  只有手动指定 / 「TUI 保真」凑列数时才套 `minCols=10`。
- 字号上下限收进 `HP.Geom.minFont=6 / maxFont=48` 一处，
  设置面板、窗口大小对话框、双指缩放**全部引用同一套**，并把放大上限从 24 提到 **48**。

**验证**（393px 宽竖屏，逐档放大字号）

| 字号 | 列×行 | 屏幕能容纳 | 渲染宽/终端区宽 | 超出 | 横滑 |
|---|---|---|---|---|---|
| 13px | 48×33 | 48 | 374/393 | −19 | 否 |
| 20px | 31×21 | 31 | 372/393 | −21 | 否 |
| 28px | 22×15 | 22 | 370/393 | −23 | 否 |
| 40px | 15×10 | 15 | 360/393 | −33 | 否 |
| 48px | 13×8 | 13 | 374/393 | −19 | 否 |

- 每一档：`pan=false`，且**列数从未超过屏幕可容纳值**（没有被抬高）✓
- 40px 字号下远端 `stty size` 回读 = `10 15`，与本地 15×10 一致 ✓
- 对话框字号输入框 `min=6 max=48`，填 40 不被夹掉；并实时提示「屏幕在 40px 字号下可容纳 15 列」✓
- 双指缩放：放大可到 **48px**（原来卡在 24），缩小止于 6px ✓

**为什么和 Termux 不一样**：Termux 不关心远端跑什么，字体多大就给多少列。
我这边一开始**故意**为了「凑够 80 列让 Hermes 的框线不错位」把终端撑宽、还缩了字号 ——
这个取舍在手机上就是错的，等于让用户为 TUI 的排版牺牲可读性和屏幕宽度。
现已改回和 Termux 一致的行为：字号你说了算，列数跟着字号和屏幕算，永不超出屏幕。

## 缺陷 14 — 界面不跟着 SSH 刷新

先用真截图取证，排除「渲染器卡死」：远端持续输出时连拍 7 张，
**7/7 全不相同、相邻 6 对全部有变化** —— 前台渲染是正常的。
所以问题在别处，查出**两个独立成因**：

**成因 A：只要有任何系统窗口盖在 App 上面，整个界面就被冻住。**
实测被权限弹窗 `GrantPermissionsActivity` 盖住后：`rAF 帧数=0`、
`setInterval` 一次都没触发、`--vh` 停在旧值 —— 界面看起来就是「卡死不刷新」。
根因是我自己在 `onPause` 里调了 `web.onPause()`（Android 13+ 的前台服务会触发
POST_NOTIFICATIONS 弹窗，正好踩中）。终端类应用必须一直活着（Termux 是前台服务 +
原生渲染，天然不会被冻），所以**改成绝不暂停 WebView**，只在回到前台时主动补一次。

**成因 B：`visualViewport` 变了却可能不派发 resize 事件。**
实测把视口高度从 778 改成 377（`visualViewport.height` 与 `innerHeight` 都变了），
`vvResize=0 vvScroll=0 winResize=0`，**一个事件都没有**，
于是 `--vh` 一直是 778，键条就停在屏幕外。所以除事件外再加一层**看门狗**：
每帧只读两个数字，变了才动布局（不做布局查询，开销可忽略）。

**另外补上"不丢输出"**：原生侧给下行输出加了 512KB 环形缓冲 + 递增 `seq`，
JS 记住自己渲染到的 seq，回前台用 `session.since(seq)` 把漏掉的补回来。
（Termux 永远不会丢输出，我们要达到同样效果就得自己留一份。）

**验证**

| 检查 | 结果 |
|---|---|
| 前台持续输出屏幕是否重绘 | 真截图 7/7 不同 ✓ |
| 视口变化后 `--vh` 是否跟上 | 778→377 时 `--vh`=377.09、键条底边 377、完整可见 ✓ |
| 补输出 | 把 rxSeq 退回后 `resyncOutput()` 补回 200 字节，追平后再调为 0（不重复刷）✓ |
| 切后台 10 秒期间产生的输出 | 回前台后 3 条一条不少 ✓ |

## 缺陷 15 — 公钥自动装到服务器（ssh-copy-id）+ 为什么要验证

**实现**：连接成功后，若主机是密码登录且选了密钥，自动把公钥追加到服务器
`~/.ssh/authorized_keys`（`umask 077` + `chmod 700/600`，幂等：已在就不重复写），
**然后用密钥真连一次验证**，只有验证通过才把主机切成密钥登录 ——
不验证就切，万一没装上用户就再也进不去了。菜单里也留了手动入口
「⬆ 把公钥装到服务器」，设置里有开关 `autoInstallKey`。

**验证**（真 sshd 在这个环境是 `PasswordAuthentication no`，且不该给系统账号设密码，
所以用 Node ssh2 起了一个独立的假服务器 `tools/testssh2.mjs`：固定口令 + 真实 exec +
读沙箱 HOME 的 authorized_keys 做公钥认证）

```
密码登录 → connected
key.install → {"ok":true,"added":true,"count":1,"verified":true,
                "msg":"公钥已装到服务器，并用密钥成功登录验证过"}
服务器侧 authorized_keys → 1 行，就是刚装的那把公钥
切成密钥登录后再连 → connected（不再用密码）
```

**排查过程中踩到的三个测试环境坑**（都不是 App 的问题，但会让人误判）：
1. ssh2 不认 Node crypto 导出的 PKCS8 ed25519 PEM → 改用 `ssh-keygen` 生成主机密钥。
2. 假服务器没接 `pty` 请求 → jsch 报 `failed to send channel request`。
3. **假服务器在拒绝最初的 `none` 探测时只回了 `['password']`** →
   jsch（被限定为 publickey）看到服务器不支持公钥，**直接放弃、根本没提交密钥**，
   报错却是 `Auth fail for methods 'password'`，极容易误判成"密码不对"。
   同一把密钥连真 sshd 是通的，才定位到这里。

> 顺带证明了一件重要的事：**同一把密钥连真 OpenSSH（2222）完全成功**
> （`connected` + 远端回显 KEYAUTH-WORKS），所以密钥生成、jsch 密钥登录路径都是好的。

## 缺陷 16 — 不能用单指向上滑动查看上面的文本

**现象**：想往上翻看之前的输出，滑不动。

**根因**：手势分流里**单指拖动从不滚动** ——
竖向拖动和横向拖动都被归到「横向平移(pan)」或「给 TUI 发鼠标拖动(drag)」；
真正的滚动被绑成**双指上下滑**（`pts.size === 2` 且间距 < 60px）。
双指滚动太隐蔽，实际用起来等于没有。Termux 是单指上下滑直接翻历史。

**修复**：单指拖动**按主导方向分流**
- **竖向** → 滚动回看历史（按实际单元格高度换算，不再是写死的 14px）
- **横向** → 平移看超宽内容（需要时）／给 TUI 发鼠标拖动

另外补一个**「⇣ 回到底部（上面还有 N 行）」胶囊**：往上翻之后新输出不会把你拉回底部
（这是对的，xterm 也是这行为），但必须给一条明显的路回去，否则会以为"滚动卡住了"。

**验证**（先造 200 行历史，用真实 PointerEvent 模拟单指滑动）

| 检查 | 结果 |
|---|---|
| 已在底部时上滑 | 不会跑到负数 ✓ |
| **单指下滑 → 向上翻看历史** | 距底部 0 → 5 行 ✓ |
| 继续滑动翻得更多 | 距底部 35 行（viewportY 134 / baseY 169）✓ |
| 能看到最早的输出 | 找到 `HIST-1` ✓ |
| 「回到底部」胶囊 | 出现，文案「上面还有 35 行」✓ |
| 点胶囊 | 距底部归 0，胶囊自动隐藏 ✓ |
| 横向拖动不触发滚动 | 滚动位置不变（方向分流正确）✓ |

> 说明：**TUI（alt 屏）里本地没有 scrollback**（xterm 的备用屏不存历史），
> 这时滑动会把滚轮事件发给远端 —— 需要远端程序自己支持滚动
> （`tmux set -g mouse on` / `less` / `htop` 这类）。Termux 上行为一样。
> 普通 shell 下的历史回看是本地的，就是上面验证的这条路径。

## 新增功能 — 终端事件通知（命令完成 / 需要授权 / 脚本主动通知）

**为什么做这个**：手机端跑 SSH 最实际的两个场景是"丢下手机去干别的"和"出事了人不在旁边"。
这两件事本质都是**需要主动叫到人** —— 原生通知是唯一可靠的手段（Termux 也靠通知）。

**五种触发，全部可单独开关**

| 触发 | 来源 | 精度 |
|---|---|---|
| **命令跑完了** | 按回车起算，输出静下来 ≥2.5s 且回到提示符 → 认为结束；只通知耗时 ≥10s 的 | 启发式，**远端零配置** |
| 命令跑完了（精确） | 远端若装了 shell 集成，`OSC 133;D;<退出码>` 直接给结束与退出码 | 精确 |
| **远端响铃** | `BEL`（`\x07`）—— 很多程序跑完/出错会响铃 | 精确 |
| **脚本主动通知** | `OSC 777` / `OSC 9`：`printf '\e]777;notify;标题;正文\a'` | 精确 |
| **需要授权 / 连接失败** | 主机指纹确认、认证失败、没有保存密码 | 精确 |

另外连接断开（默认关，避免频繁弹）、公钥安装结果也会通知。

**设计上的几条纪律**
- **前台不打扰**：App 正在前台时普通事件不发通知（用户正看着，弹通知是噪音），
  只有 urgent 类（需要授权）能穿透。
- **同类节流**：避免某个程序疯狂输出 BEL 把通知栏刷爆。
- 点通知回到 App 并把终端滚到底。
- 没拿到通知权限就安静地不发，不抛异常。

**验证**（把 App 切到后台 = 模拟"手机放桌上"，再触发三类事件；读系统通知栏取证）

```
=== 通知栏实收（本 App）===
  android.title=String (命令已完成（15 秒）)
  android.text=String ($ sleep 12; echo ALL-DONE
  android.title=String (构建完成)
  android.text=String (用了 42 秒，3 个警告)          ← OSC 777
  android.title=String (终端响铃)
  android.text=String (fp · 远端发出了响铃（常见于命令跑完/出错）)   ← BEL
  android.title=String (首次连接，需要确认主机指纹)
  android.text=String (10.0.2.2:2222                  ← 需要授权
```

前台抑制与紧急穿透：

| 场景 | 结果 |
|---|---|
| 前台 + 普通事件（响铃） | `posted=false`，`foreground=true` ✓ 不打扰 |
| 前台 + 需要授权 | `posted=true` ✓ 必须让你知道 |
| 关掉「通知：远端响铃」开关后触发 | 不再发 ✓ |

**顺带修掉两个真 bug**
1. `lastVisibleLine()` 只看缓冲**末尾 12 行** —— `clear` 之后内容在顶部、下面全是空行，
   于是判定拿不到提示符、命令完成通知根本不触发。改成从**光标所在行**往上找。
2. watcher 回调签名是 `onChange(kind, watcher, data)` 三个参数，我接成了 `(kind, data)`，
   于是 `data` 收到的是 watcher 对象、载荷全丢 —— 表现是 OSC 通知标题为空串
   （`notifyEvent 被调用: [{"k":"osc","t":"","u":true}]`）。
   这个错误很隐蔽：不报错、不崩溃，只是"通知发了但内容是空的"。

## 缺陷 17 — 下拉还是看不到上面的文本（真机手势 + TUI 两回事）

**先说验证方法的问题**：上一轮我用的是**合成 PointerEvent**（`elementFromPoint` + `dispatchEvent`），
它**绕过了浏览器的触摸手势仲裁** —— 等于没测到真机上的行为。这轮改成
`Input.dispatchTouchEvent` **真实触摸注入**，立刻看到真实序列：

```
pointerdown@300 → pointermove@321 → pointercancel@0     ← 拖动被掐断
```

**三个成因，逐个查清**

1. **浮层吃掉手势**：第一次真实触摸测试时，顶到的是开着的 `#overlay`（设置面板），
   竖向手势被面板的原生滚动拿去，应用只收到 1 个 move 就被 `pointercancel`。
   顺带查出 `#toast` **没有 `pointer-events: none`** —— 提示条浮在终端上方，
   它盖住的那块开始拖动就"怎么滑都不动"。已给 toast 加 `pointer-events: none`。
2. **没有声明 `touch-action`**：`#stage` 上没写，浏览器会自行仲裁手势。
   已加 `touch-action: none`（面板 `#overlay` 保留 `pan-y`，它本来就要能滚）。
3. **TUI 里本来就没有本地历史**（这条才是"下拉没反应"最可能的原因）：
   xterm 的**备用屏不存 scrollback**，全屏 TUI（Hermes/tmux/vim）下往上滑
   只能把滚轮事件发给远端 —— 远端没开鼠标模式就等于没反应。
   以前这里只弹一句被动提示，用户多半没注意。现在改成**可一键解决**：

   实测（真 TUI = tmux，独立 socket）：

   ```
   ① 进入 TUI:  鼠标模式=0   顶栏「TUI·滚动受限」
   ② 下拉:      弹出「TUI 里没有本地历史可翻…要我帮你开 tmux 鼠标吗？」
                [开启 tmux 鼠标] [取消]
   ③ 点按钮:    鼠标模式=1002  顶栏「TUI·鼠标」   ← tmux 真的开了鼠标上报
   ④ 再下拉:    发出 13 个滚轮序列 → 由 tmux 自己滚
   ```

**真实触摸 A/B（shell 场景）**

| | pointermove | pointercancel | 距底部 |
|---|---|---|---|
| 下拉 320px（第 1 次） | 15 | **0** | 0 → 15 行 |
| 再下拉 320px | 30 | **0** | 15 → 30 行 |
| 横拖 160px | 44 | **0** | 30（不变）✓ |

**要注意的一点**（诚实说明）：`touch-action: none` 这一条，在"面板关掉"的对照实验里
并不是决定性的（`auto` 也能收到 30 个 move）；它是**正确的加固**（不让浏览器抢手势），
真正卡住用户的是浮层吃手势 + TUI 没有本地历史这两条。

## 缺陷 18 — 「发送」那一栏不实时（要敲完点发送才整行进去）

**现象**：屏幕弹出键盘打字是实时的、下面 Esc/Tab 那些键也是实时的，
**只有「发送」那一栏不是实时的**。

**成因**：输入框（composer）从设计上就是"攒着"的 —— `sendComposer()` 只在点「发送」
或按回车时把 `ta.value` 整行送出去。交互式界面（TUI、密码提示、REPL）里等于没键盘。

**改法**：输入框变成**按键直通管**，和点功能键条走同一条链路：

- `keydown` 逐键处理：回车→`\r`、退格→`\x7f`、Tab→`\t`、Esc→`\x1b`、方向键→CSI 序列、
  可打印字符原样；命中就 `preventDefault()`（所以框里不留字）。**修饰键（Ctrl/Alt）一并套用**。
- `input` 事件兜住输入法上屏 / 粘贴的一整批字符（中文走这条），原样送走不加回车。
- 想回到"攒着"：输入框左边多了个「实时 / 攒着」开关（设置里也有 `liveComposer`），
  攒着模式下「发送」按钮恢复原义，实时模式下按钮变成「⏎」（空框时＝发一个回车）。

**实测**（真实 CDP 注入到输入框）：

```
敲 l            → 发送 ["l"]
敲 s            → 发送 ["l","s"]
中文上屏         → 发送 ["l","s","中文测试"]
回车 / 退格 / Tab / Esc / ↑ → 0xd / 0x7f / 0x9 / 0x1b / 0x1b[A
点「⏎」按钮       → 0xd
输入框内容：全程为空
```

**补：中文输入法的坑（真机才会遇到，模拟器 `insertText` 测不出来）**

真机用中文输入法时，事件顺序是「compositionstart → 组合中不断 input → **改 textarea.value** → compositionend」，
而组合期间的 `input` 我们本来就该跳过（半成品不能进终端）。第一版只在 `compositionend` 里把标记清掉、
**没有补发**，结果就是：手机上打中文 → 字留在输入框里、**什么都没进终端**，
看起来完全就是"这一栏不实时"。已改成在 `compositionend` 里补发上屏内容并清空输入框。

用合成事件还原真机顺序验证：

```
组合中（compositionstart + input(comb)）→ 发送：[]        输入框：zhongwen   ← 半成品不发，正确
上屏（compositionend，value=中文）      → 发送：["中文"]   输入框：空
再 insertText 一段                      → 发送：["中文","粘贴或英文"]
```

## 缺陷 19 — TUI 里按不到 Ctrl（"输入 ctrl+b d 退不出 tmux"）

**两个成因，缺一不可**

1. **键条的 TUI 行里根本没有 Ctrl/Alt**。Ctrl/Alt 只存在于 shell 行（TUI 下整行隐藏）
   和「⌄更多」展开行（要点一下才出来）。而 TUI 恰恰就是 tmux/vim/less 待的地方，
   tmux 的操作几乎都要 Ctrl —— 用户只能得出"按不出来"的结论。
   已把 Ctrl/Alt 挪进 TUI 可见行（`⇞回滚`、`⌨键盘` 挪去「⌄更多」）：
   实测 TUI 可见行的键 = `Esc Tab ⇧Tab ↑ ↓ ← → ⏎ Ctrl Alt ⌫ ^C PgUp PgDn ▤ ⌄更多`。
2. **键盘输入不看 Ctrl 锁定**。`term.onData` 原来是 `this.send(d)` 一把梭，
   于是"点键条 Ctrl（亮起来）→ 在键盘上敲 b" 发出去的是普通 `b` 而不是 `C-b`，
   而且那个 Ctrl 会一直亮着不消。已改成与键条共用同一条修饰键链路（多字符只套第一个字符）。
   顺带修掉：锁定修饰键后必须把焦点还给终端，否则软键盘会被收起、没法接着敲那个字母。

**实测（真 tmux，独立 socket）**

```
点 Ctrl          → 锁定Ctrl=true，焦点在终端=true
敲 b             → 发送 ["C-b"]        ← C-b 真的发出去了
敲 d             → 发送 ["C-b","d"]，TUI:true→false，顶栏「TUI·滚动受限」→「shell」
tmux 端：客户端列表为空（已脱离）；会话 cb1 仍在（只是 detach，没被 kill）
```

## 缺陷 20 — 发送时重复推送窗口尺寸，TUI 被逼整屏重画（"发送后有延迟"）

**怎么发现的**：先量了管道本身 —— 发出→收到远端回显 4.5/8/10.3ms、解析 1.3-2.2ms、
绘制 10.7-11.7ms，**合计 16-24ms（一帧）**，渲染不慢。于是改量发送前后的时间线，
立刻看到一串重排：

```
输入框点「发送」: 5 次重排 + 3 次 session.resize RPC
终端里直接回车:   4 次重排 + 2 次 session.resize RPC
                 ↑ 尺寸全程是 48×33，压根没变
```

**根因**：`resetGeometry()` 里那句 `session.resize` 是**无条件**发的
（`Geom.apply` 内部其实已经对 `term.resize` 做了短路，漏的是这一句）。
而远端每收到一次窗口尺寸变化就收一次 SIGWINCH，TUI（tmux/Hermes/vim）要**整屏重画** ——
连发 3 次就是重画 3 次，这就是"点了发送之后终端要等一会儿才更新"。

**改法**：加 `pushResize(cols, rows)`，同一个（会话, 列, 行）只发一次，换会话时清空记录；
两处发送点都走它。**实测 resize 次数 3 → 1**（剩下的 1 次是新会话首次同步）。

## 缺陷 21 — 按了 Esc 之类的功能键，软键盘会被收起

**成因**：键条上的键是 `<button>`。点它会**把焦点从输入框抢到按钮上**，
Android 的输入法随之收起 —— 按一下 Esc 就得再点一下屏幕把键盘叫回来，极难用。

**改法**（三步，缺一不可）：

1. `pointerdown` 上 `preventDefault()`：拦掉这次焦点转移。
2. **动作改由 `pointerup` 触发**。只挂 `click` 会失效 ——
   实测 Chromium 会把被 `preventDefault` 掉的那次 pointerdown 之后的 `click` **一起吞掉**，
   表现就是"按了没反应"（这个坑我踩了：改完第一版 Esc 直接不发）。
   `click` 保留做兜底（键盘激活/无障碍），并用时间戳避免与 pointerup 重复执行。
3. 动作做完把焦点**还给"按之前正在输入的那一位"**，而不是无脑 `term.focus()`：
   在输入框里打字时点 Esc，应该继续留在输入框里打字。

**实测（真实手势 `Input.synthesizeTapGesture`）**

```
事件序列: pointerdown(可取消) → touchstart → pointerup(可取消) → touchend → click
点 Esc      → 发出 ["0x1b"]   焦点仍是终端 TEXTAREA    ← 键盘不会被收
点 Ctrl     → 锁定Ctrl=true   焦点仍在原来那一处
点「⌄更多」  → 更多行展开
```

**顺带揪出两个真 bug**

- **`⌄更多` 会漏发一个杂散键**：展开那一瞬间键条整体位移，这一击残留的 `click`
  落到了"刚冒出来"的那个键上（实测多发一个 `Ctrl+空格` = 0x0）。
  已在 `toggleMore()` 里开 350ms 的短窗口，让残留 click 不生效。**实测杂散字节消失。**
- **输入框里锁定 Ctrl 后打字母不带修饰键**：手机上字母**多数是输入法"提交"**
  （走 `input` 事件）而不是 `keydown` —— 我原来只在 keydown 里套修饰键，
  于是真机上"点 Ctrl 再敲 b"发出去的还是普通 `b`，**Ctrl+b 永远按不出来**
  （模拟器用 `insertText` 测也不会暴露，因为它走的是另一条路）。
  已抽出统一的 `sendLive()`，keydown / 输入法上屏 / 粘贴三条路都过它。
  **实测：输入框里点 Ctrl 再敲 `x` → 发出 `0x18`（Ctrl+X）。**

## 缺陷 22 — 工具自身：cdp.mjs 的 `tap` 传坐标时会静默跳过

排查上面几条时，"真实点击"反复点不动，最后发现是**我自己的测试工具**在骗人：
`tools/cdp.mjs` 的 `tap` 只认选择器（`{"tap": "#btn"}`），
传坐标对象（`{"tap": {"x":28,"y":708}}`）时它记一条 `元素不可见或不存在` 就**继续往下跑**，
既不点击也不报错 —— 于是"应用没反应"排查了好几轮，其实压根没点。

已修：支持坐标写法；目标不可见/不存在时**直接抛错**，不再静默跳过。
另外选择器要落在**当前可见**的那一行键条上（TUI 模式是 `#krow-tui`，shell 模式是 `#krow-shell`），
拿错行同样是"元素不可见"。

## 新增功能 — 流量统计（下行 / 上行）

**要什么**：统计下行的数据量。

**怎么做**（两份计数，互相印证）

| | 数什么 | 在哪 | 怎么算 |
|---|---|---|---|
| **渲染侧** | 实际送进终端渲染的字节 | JS `onData` | `traffic.down += bytes.length`，顺带记数据块次数 |
| **上行** | 发往远端的字节 | JS `send` | 按 UTF-8 算（`HP.enc.encode(d).length`） |
| **socket 侧** | 网线上真实收发的字节 | 原生 `Ssh.kt` | 已有的 `bytesIn/bytesOut`，随 `metrics` 事件过来 |

两份都留不是冗余：**回前台补发**（环形缓冲 `since`）会让渲染侧比 socket 侧多，
"差额"那一行正好用来看补发了多少。

**界面**

- 顶栏一格 `↓ 981.9K`（可关，设置里 `showTraffic`）；点开是详情：
  下行总量/速率/峰值、上行、平均下行、会话时长、收到数据块、**服务端 socket 计数**、
  **差额**、跨会话累计下行；带「计数归零」。
- 长按终端菜单里也有一项「📊 流量统计」。

**性能**：统计本身只是两个整数相加；每秒采样一次算速率（指数平滑），
**顶栏那个数字没变就不碰 DOM**（终端类 App 最忌每帧动布局）。

**实测（用已知大小的数据核对，不是"看着像"）**

```
基准                                  下行 169B / 上行 6B
拉 1,000,000 字节：head -c 1000000 /dev/zero | tr '\0' A
  → 下行增量 1,000,095  ← 多出的 95B 正是命令回显 + 提示符
发 5,002 字节（'#' + 5000 个 x + 回车）
  → 上行增量 5,002      ← 精确到字节
详情对话框（实时刷新）：
  下行（收到）981.9K   下行速率 4.1K/s   峰值 438.1K/s
  上行（发出）4.9K     上行速率 625B/s
  平均下行 63.5K/s     会话时长 15 秒    收到数据块 82 次（平均 12.0K）
  服务端 socket 981.9K ↓ / 4.9K ↑      差额（补发等）+0B
  累计下行（跨会话）981.9K
```

顺带修掉一个显示 bug：顶栏原来把 `bytesIn`（**下行**）标成了 `↑`（上行），方向是反的。

## 缺陷 23 — 通知收不到：没权限是**静默丢弃**，而且应用里根本没有授权入口

用户原话："我没收到，我不知道在哪授权"

**三个叠加的问题**

1. 没有权限时，系统对通知的行为是**静默丢弃** —— 不报错、不提示。所以"收不到"没有任何线索。
2. 应用里**没有任何授权入口**。清单里声明了权限、`onCreate` 里也申请过一次 ——
   但用户第一次点了"不允许"（或压根没注意到那个弹窗）之后，就再也找不到地方授权了。
3. 前台收到普通通知时**什么都不发生**（按设计不打扰），看起来也像"没收到"。

**改法**

- 连上之后**主动自检**：没权限就弹一个说清楚的框（"没有权限时通知会被系统静默丢掉…现在去授权？"），
  按钮一点就拉起系统权限申请。
- 设置面板新增「通知权限」卡片：**实时状态**（已授权/未授权 + 现在是前台还是后台）
  \+ 三个按钮：`申请通知权限` / `打开系统通知设置` / `发一条测试通知`。
- 长按终端菜单加一项「🔔 通知自检（权限 / 测试通知）」。
- 授权成功后原生回调前端 → **立刻发一条测试通知**（"通知已就绪"），当场确认链路通。
- 前台收到普通通知时，除了不发系统通知，**改成应用内浮一条** ——
  "什么都不发生"是最容易让人误判成 bug 的行为。

**实测（撤权限 → 冷启动 → 走完整条链路）**

```
撤销权限后启动 : 系统弹窗 com.android.permissioncontroller.GrantPermissionsActivity ✓
返回键取消     : granted=false（= 用户点了不允许）
连上后         : 弹出说明框；点「去授权」→ 系统权限弹窗**重新拉起**（窗口 id 变了 ✓）
真点弹窗的 Allow: granted=true（flags 里带上 USER_SET）
授权后         : 应用内显示「已授权 · 现在是「App 前台」」；
                 自动自测通知「通知已就绪 / 以后远端有事，我就这样叫你」落到通知栏 ✓
前台再发普通事件: 系统通知 posted=false（按设计不打扰），应用内浮出「通知文本测试：应该浮出来」✓
```

## 新增功能 — 在手机上看 Hermes 的技能与记忆

需求：「能够查看 hermes 的 skills 和 memory」。

**做成了面板第 4 个标签页「Hermes」**（不用退出终端，侧边就看）：

- **记忆**：`USER.md`（关于你）+ `MEMORY.md`（我的笔记）全文，各自带占用比例
  （上限从远端 `config.yaml` 的 `memory_char_limit` / `user_char_limit` 读，实测 2200 / 1375），
  并标出条目数（`§` 分隔）。
- **技能**：按目录分类列出全部技能（实测 62 个 / 12 类），带 `description`、路径、字节数；
  **点开看 SKILL.md 全文**，还能一键「在终端打开」（`less`），看完按 `q` 退出。
- 只有真的停在这一页才去读远端 —— 打开面板不会顺手拉 60 个文件。

**取数怎么做的**

- 复用**终端那条会话**开临时 exec 通道（`SshSession.exec`，自带超时：远端卡住就断开通道，
  面板不会一直转圈），不新开连接、不打扰终端。
- 命令是**固定字符串**，用户输入只出现在"读某个技能"的路径里，那个走严格字符集校验
  （只放行 `skills/` 与 `memories/` 前缀，禁 `..`）。
- 用 `find -printf` 一次拿全量（路径/大小/时间）、`find -exec grep -H` 一次拿全量描述 ——
  避免"每个技能起两个子进程"（62 个技能 = 120+ 进程，面板会明显卡）。

**实测**

```
hermes.info   → 目录 /home/lwgat/.hermes，技能 62，分类 12，
                记忆上限 2200 / 用户画像上限 1375，
                样例 software-development/github/SKILL.md · 2446 字节 · "GitHub via gh CLI: ..."
hermes.memory → MEMORY 1583 字符 / 8 条，USER 152 字符；首行与远端文件逐字一致
面板渲染      → 62 个技能行 + 12 个分类标题；USER.md 11%（152/1375）
点开 github   → 弹窗内容 "--- name: github description: ..."
在终端打开    → less 打开该技能，终端里出现 name/description/tags 三行
```

### 顺带修掉的两个真问题

**缺陷 24 — 分隔符被"吞"：记忆内容整段串位。**
取记忆时用 `@@USER` / `@@MEM` 做区段标记，但**两个记忆文件末尾都没有换行符**，
于是 `echo @@MEM` 粘在正文尾巴上（`…再重做。@@MEM`），标记行永远匹配不到 ——
结果 MEMORY.md 的内容被整段并进了 USER.md（实测 1746 字符，显示 127%，而 MEMORY 是空的）。
两处修：标记前后强制 `printf '\n@@X\n'`；解析端再加一层"标记粘在行尾也能拆开"的兼容。

**缺陷 25 — Kotlin 的块注释是**可嵌套**的，注释里写通配路径会把文件后半段吃掉。**
我在注释里写了记忆目录的通配写法（斜杠紧跟星号），那个序列被 Kotlin 当成嵌套注释的开始，
外层注释再也不闭合 → 报错是莫名其妙的 `Unclosed comment`（还连带报出 `Missing '}'`、
`Unresolved reference: dispatch` 这种完全误导人的错）。**注释里永远不要出现"斜杠+星号"**。

## 新增功能 — 省电板块（省电，但尽量不断连）

需求：「添加一个板块就是省电，我希望你做到一些省电功能。但是尽量保持链接的存活」。

**核心取舍：省电 ≠ 断连。**

待机耗电的大头从来不是“连接本身”，而是两件事：
① **一直握着 CPU 唤醒锁**（PARTIAL_WAKE_LOCK）—— CPU 永远睡不着；
② **一堆定时器反复把 CPU 拽醒**（每秒的统计、每 20 秒的心跳、睡着时的重连风暴）。
所以省电的做法是：**TCP socket 留着（内核维持，不花我们的 CPU），只把我们自己花 CPU 的活停掉**，
亮屏回来再用既有的环形缓冲（`session.since`）把睡着期间漏掉的输出补回来。

**省电时具体停掉什么**

| 动作 | 之前 | 省电中 |
|---|---|---|
| CPU 唤醒锁 | 一直持有 | **释放**（CPU 真能睡） |
| SSH 层心跳 | 每 30 秒 | **拉长到 120 秒**（不是关！关闭会被 NAT/中间设备当成死连接掐掉，与「连接不要断开」直接冲突） |
| 终端渲染看门狗 | 每帧 rAF | 取消 |
| 流量采样 / 命令完成判定 | 每 1 秒 | 停 |
| App 层心跳 ping | 每 20 秒 | 停 |
| 断线自动重连 | 睡着也反复重连 | **暂缓**（亮屏立刻补上） |
| **TCP 连接** | 有 | **仍然有**（这就是"保持存活"） |

**实测（每一步都有原生/服务端证据）**

```
① 前台基线   省电=false，唤醒锁=持有(PARTIAL_WAKE_LOCK 'hermes-pocket:ssh')，
             定时器(流量/命令判定/心跳)全在，看门狗在；服务端连接 2 条
② 切后台     省电=true，wakeHeld=false（唤醒锁**已释放**），定时器全停，看门狗停
             ← 服务端连接仍是 2 条：**没断**
③ 睡着期间   远端照常产生输出（DOZE-OUTPUT-1789616455 / SECOND-LINE）
④ 回前台     省电=false，唤醒锁收回，会话状态仍是 connected（**没有重连**）
⑤ 输出核对   终端缓冲里 DOZE-OUTPUT / SECOND-LINE 都在 —— **睡着了也没丢输出**
⑥ 息屏路径   息屏 → save=true, interactive=false, 唤醒锁释放；
             唤醒 → save=false, 唤醒锁收回
```

**可调项**（设置 → 省电，另有「立刻省电一次 / 立刻退出省电 / 刷新状态」三个按钮）

- 省电模式：关 / **息屏时省电（默认）** / 后台+息屏省电
- 息屏后延迟多久进入省电：立即 / 1 分 / 5 分 / 15 分
- 保持唤醒（原有）：开着链接最稳（能扛整夜 Doze），代价是一直占 CPU；省电模式会在息屏时**临时**放开它

一点诚实说明：页面被隐藏时 Chromium 本来就会暂停 `requestAnimationFrame`，
所以「取消看门狗」这条省不了多少；真正省电的是**释放唤醒锁**和**停掉那几个 setInterval**，
以及**不在睡着时反复重连**。这三条都有上面的实测证据。

## 新增功能 — 省电第二轮：后台不渲染 → 落盘 → 回前台再渲染（连接绝不断）

需求（逐字）：「连接不能断开……如果这终端是在运行的，他一直在连着，然后呢，我时时保持连接，
然后呢，把它写入到缓存或者是写入到硬盘中存储下来，然后等他到前台之后，他再做渲染。这种的。
特别重要的就是连接不要断开，请不要断开。断开的话就需要什么，重连，重连的话就需要能够获得
我之前没获得的信息。」

**这一轮把省电的做法改对了三处：**

1. **后台真的不渲染** —— 原来只是"JS 少做点事"，现在**原生层直接不发 `data` 事件**：
   数据进内存环形缓冲（512KB）+ 追加落盘，前端一个字节都不碰。
   好处是后台不花 CPU 解码/绘制，WebView 被系统节流时也不会堆一堆消息等着炸。
2. **心跳不能关，要拉长** —— 上一轮省电时我把 SSH 心跳静音了（0=关），这是错的：
   NAT / 移动网络 / 中间设备会把长时间没流量的 TCP 当成死连接回收掉，"省电"直接把连接省没了。
   现在省电期间心跳 **30s → 120s**（保住 NAT 映射，又不至于频繁唤醒 CPU）。
3. **落盘缓存（不只是内存）** —— 省电期间的输出同时写 `files/spill-<会话id>.log`，
   容量 1MB（内存环形缓冲只有 512KB，而且进程一被杀就没了；落盘这份扛得住进程被杀）。
   写入是**追加**，满了就不再写（不覆盖、不做复杂轮转，简单可靠）。

**回前台补渲染的顺序**（顺序错了会把新数据插到旧数据前面）：

```
① 前端置 _flushBuf=[]（此后收到的事件先攒着，不渲染）
② 取走落盘缓存（此时原生还在省电态，不会有新事件插进来）
③ 关省电 → 事件恢复
④ 把落盘的那段按顺序写进终端（并喂给通知嗅探器）
⑤ 放行攒下的事件（只处理 seq 比缓存更晚的，避免重复）
```

**实测（模拟器 + 服务端双侧证据）**

```
① 前台基线   渲染水位=6，终端总行数=32，落盘缓存=无，服务端连接 2 条
② 切后台     省电=true(原生确认)，连接数 **仍是 2（没断）**，心跳=120s，唤醒锁=已释放
③ 后台产生   远端输出 2000 行（BG-LINE-TEST×2000 + BG-DONE）
             渲染水位 **仍是 6**、终端总行数 **仍是 32**  ← 后台一个字节都没渲染
             落盘缓存 spill-2ff6c045a27e4de0.log = **28114 字节** ← 数据在这里
             连接数仍是 2
④ 回前台     渲染水位 6 → **67**，终端总行数 32 → **2002**  ← 落盘的那段补渲染出来了
             落盘缓存已被取走并清空（文件没了），连接数仍是 2
```

**真断线 → 自动重连 → 回到原会话**（这一条专门验"重连要能拿到之前没获得的信息"）

```
① 掐断服务端该连接的 sshd 会话进程（真断线；保留监听者好让重连有目标）
② 3 秒内应用就发现：状态 connected → reconnecting（顶栏"重连中…"），服务端连接数掉到 0
③ 6~10 秒后自己连回来：状态 → connected，服务端连接数恢复 2 条
④ 断线前的输出仍然在终端里（BEFORE-DROP-3 还在）
   ← 因为会话对象没被销毁，环形缓冲跨重连保住了；重连后 `session.since(渲染水位)` 补齐
⑤ 重跑了主机配的启动命令（REATTACH-MARK …）→ 用户回到自己原来的会话（配 tmux 就是回到 tmux）
```

**新增开关**：设置 → 省电 增加「重连后自动回到原会话（重跑启动命令）」（默认开）。

**顺带修掉一个隐蔽 bug**：连接时用的是**面板缓存**里的主机配置，缓存可能是旧的
（在别处刚改过启动命令/密钥），会出现"明明配了启动命令却不执行"。改成连接前取一次新鲜的 `host.list`。

**测试方法上的两个坑（记下来免得下次再踩）**

- `tools/testssh.sh stop` **不会断掉已建立的会话**：它只停监听者，老会话进程还活着，连接照样通。
  想测真断线必须**按 PID 杀掉该连接的 sshd 会话进程**（`ss -tnp` 里取 pid，排掉监听者）。
  我在这上面白跑了两轮，还一度误以为"断线后不重连"。
- 重启测试 sshd 会**重新生成 host key 和 authorized_keys**（临时目录被清时），
  于是应用会弹"主机指纹变更"、并且手里那把私钥不再被接受 —— 这是 TOFU 的正常安全行为，
  不是缺陷；测试时要重新确认指纹 + 把应用公钥装回 `authorized_keys`。
