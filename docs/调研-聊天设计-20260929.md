## 1. 发送状态的提示（对应 `R-52`）

### 1.1 位置：气泡前 / 内 / 旁 —— 三家现成做法

| 出处 | 做法（公开可见/官方） |
|---|---|
| **Telegram**（官方 FAQ `telegram.org/faq`：「What do the check marks mean?」） | 状态**在气泡内**：一个对号＝已到 Telegram 云端（并已通知对方）、两个对号＝对方**已读**；等待发出时是**时钟图标**（第三方解释稿 techmesto：Clock icon = pending）。**Telegram 不做"已送达设备"档**（官方原话：因为它可能同时跑在很多设备上） |
| **Signal**（支持页 `How do I know if my message was delivered or read`；**该页 curl/浏览器都被 Cloudflare 挡下 403，此处引用搜索引擎回传的该页原文摘要**，标"未逐字核"） | 四档**在气泡上**：**Sending**（正在发出）→ **Sent**（已到 Signal 服务）→ **Delivered**（已到对方设备）→ **Read**（对方已读，双方都开已读回执才显示） |
| **QQ / 微信**（公开可见行为；QQ 红叹号有腾讯官方公告佐证，见 1.3） | 状态**在气泡外沿/旁边**：发送中在气泡旁转圈、失败在气泡旁出**红色感叹号**（可点重发）。**微信成功态不打勾**（这是公开可见行为，**官方帮助文档里查不到明确描述 ⇒ 标"未查证"**） |
| **我们的现状**（`talk.js:1273-1279`） | 状态＝**气泡下面另起一条** `#tk-sends`（`[data-testid="talk-sendrow"]`），三态文案 `发送中…` / `已送达` / `没送达：超时`（`talk.js:1210-1231`，3s 转"还在发…"、8s 转超时） |

**我们的建议（位置）**：**并进气泡那一行，且默认不另起状态条** ——
① 发送中/成功＝气泡**右下角小图标**（不占额外高度）；② 失败＝气泡行尾**红叹号**（可点重发）；③ `#tk-sends` 这条常驻行**只在失败时**出现，成功态不再显示（他原话"藏在气泡前面…而不是在下面"）。
**代价**：只动 `talk.js`（`repaintSends/fillSends` 改挂到气泡节点）+ `talk.css`（气泡内联图标 + 行高）；**平台侧零改动**（RPC 与回执不变）；**要重出包**。图标用**内联 SVG/纯 CSS**（离线、零依赖，不进任何 CDN）。
**判据（要能测）**：
- 三态各给一次读数（`发送中`→气泡内出现小圈；`已送达`→小圈变对号；`失败/超时`→红叹号）；
- **位置与高度**：图标前后量 `document.querySelector('.tk-bub').getBoundingClientRect().height`，**差值 = 0px**；图标中心与气泡右内边距偏差 **≤2px**；图标尺寸 **≤14px**；
- 成功态 `#tk-sends` 节点数 **= 0**；失败态 **= 1**；
- 现有 `R-31` 的 9 条发送状态断言**不回归**（3s/8s 口径不变）。

### 1.2 图标序列（小圈 → 对号 → 双对号）

| 出处 | 图标序列 |
|---|---|
| Telegram（官方 FAQ + techmesto 解释稿） | 时钟 → **单勾**（到云端）→ **双勾**（对方已读） |
| Signal（支持页摘要，同上未逐字核） | Sending（转圈）→ Sent（单勾）→ Delivered（双勾）→ **Read（实心/着色双勾）** |
| WhatsApp（第三方说明，公开可见） | 时钟 → 单灰勾 → 双灰勾 → **蓝双勾**（已读） |
| 微信（公开可见行为，**官方文档查不到**） | **不打勾**：只有"发送中"的圈，成功后无标记 |

**我们的建议**：**只用两档 —— 小圈（发送中）→ 单对号（已送达）**；**不做"已读"，不做"双对号"**。
**理由（落我们的实际）**：`roles-chat` 的 `msg` 表**没有"对方已读"字段**，App 也拿不到已读事件 ⇒ 双勾/蓝勾会变成**假信息**（这是他的验证文化里最忌讳的）；另外我们是"人 → agent"的异步消息，"已读"语义本身不可靠。
**代价**：`talk.css` 10–20 行 + 两个内联 SVG；**要重出包**。
**判据**：DOM 里图标类型**恰好 3 种**（`.tk-ic-sending` / `.tk-ic-sent` / `.tk-ic-fail`）；页面文本中**不出现"已读"二字**（`grep` 读数）；**不做**已读相关 RPC（`talk.*` 调用数不增）。

### 1.3 失败态怎么表现（红叹号 / 点击重发）

| 出处 | 做法 |
|---|---|
| **QQ**（腾讯云开发者社区 2018-05-09 报道 + 引用的**腾讯 QQ 官方公告**） | 消息旁出现**红色感叹号**；官方公告原话："部分用户发送 QQ 消息之后，出现红色感叹号，而消息实际上是发送成功的" ⇒ 红叹号＝**发送异常提示**，且**系统故障时会出现假失败**（这条对我们有借鉴：**失败态要能自证**，不能只靠图标） |
| Telegram / Signal（公开可见行为 + 支持页摘要） | 消息旁红色感叹号，**点它可重发**；Signal 支持页另有"消息待发出"的排查指引（等待对方联网） |
| 我们的现状 | 8s 无回执 → 文案"没送达：超时（8 秒没回执）"（`talk.js:1340`），**没有可点的重发** |

**我们的建议**：红叹号**可点即重发**（同一条重投 `talk.say`，不新建气泡）；连点有闸（现有"上一条没落定才挡连点"的规则保留，`talk.js:1326`）；重发后回到"发送中"小圈，8s 仍无回执仍回红叹号；**不弹窗、不长按菜单**。
**代价**：`talk.js` 一处点击绑定 + 一次重投；**要重出包**。
**判据**：点红叹号 → `talk.say` 调用数 **+1**、气泡数**不变**、状态回"发送中"；3 次连点 → **1 次**投递（防重复闸有效）；失败态点击后 8s 仍无回执 → 回到红叹号（不静默消失）。

### 1.4 状态刷新频率（他问过"多少次监听一下"这类参数）

**建议**：**沿用现有口径**（500ms 状态表；有在途消息才跑、空闲自停；省电档停表）——已实测过、不为了这条再动。
**判据**：空闲 30s 内状态表**不跑**（定时器读数）；有 1 条在途时 500ms 刷；省电档期间不刷（`R-25` 断言不回归）。

## 2. 删除聊天历史（对应 `R-53`）

### 2.1 三种语义是什么、哪些平台怎么做

| 语义 | 含义 | 现成做法与出处 | 对方还看得见吗 |
|---|---|---|---|
| **① 本地删除**（只删自己这份） | 删除本机/本端的记录 | 微信/QQ 的"删除该聊天""清空聊天记录"＝**本端动作**（**公开可见行为；官方帮助文档查不到明确说法 ⇒ 标"未查证"**，第三方说明：[数据蛙](https://www.shujuwa.net/weixin/how-to-recover-wechat-records) 等）；企业微信帮助页把"删除"与"撤回"分开列，并说"**已删除的消息不能撤回**"（`open.work.weixin.qq.com/help2/pc/14923`） | **看得见**（对方设备上照旧） |
| **② 撤回**（对双方生效，**有时间窗**） | 一定时限内让消息在对方那里消失 | **微信**：2 分钟内可撤回；撤回后 **5 分钟内可"重新编辑"**；**新增**"撤回本次发送的全部消息"（连发多条一键撤）、**文件 3 小时内可撤回**、**自己页面那行"你撤回了一条消息"可以删掉（对方页面的仍在）**（新华网转载"微信时刻"2026-08-08）；**企业微信**：内部 24 小时 / 与微信联系人 2 分钟（WeCom 帮助 14923）；**QQ**：2 分钟（公开可见行为，官方帮助页本轮**没找到** ⇒ 标"未查证"） | **看不见**（但通常**留一条系统提示**；微信那条提示本人可删、对方页仍在） |
| **③ 真删/对双方删除** | 平台与服务端一起删 | **Telegram**（官方 FAQ 原话）："You can always delete any messages you sent or received for both sides in any one-on-one conversation… deleted messages do not leave a mark in the chat"（**单聊无时限、不留痕**）；群/云聊里对别人的消息**只有 48 小时内**能"delete for everyone"（HowToGeek 说明稿）；**Signal**：支持页标题即 `Delete for everyone`，**限 24 小时内、best-effort（尽力而为）**、**被引用回复的原文不会被删**（支持页摘要，未逐字核） | **看不见**（Telegram 单聊连痕都不留） |

### 2.2 误删怎么救

| 出处 | 救法 |
|---|---|
| Telegram / Signal | 官方口径是"**尽力删，不保证**"，没给回收站；Telegram 你删了对方那边的记录也消失（不可逆） |
| 微信/QQ | 撤回留系统提示（相当于留痕）；本地删除**不可逆**（要靠备份/第三方工具，非官方） |
| **我们的现状（重要）** | 权威源是 `roles-chat/talk/*.md` **文本台账**（可回溯、可审计）+ `sqlite` 的 `msg` 表；`msg` 表已有 `hidden` 字段，但它的语义是"**隐形对接信息**（只入库、不写文本日志、不建唤醒、不进面板/推送）"（`talk.py:280-296`）——**不是"用户删历史"** |

**我们的建议（= `R-53` 原候选 B 落地版）**：**做"从我这儿删掉"（平台侧标记隐藏），但另开一个语义，不复用 `hidden`**：
- 新增 `msg.hidden_by_user`（或独立表 `msg_hide(msg_id, by_role, at)`），含义="**本人/某角色在界面里不要看到它**"；
- App 给**两档**入口（长按气泡弹小菜单，≤3 项）：**删这条** / **清空这个会话**（只影响本端视图）；
- **不做**"对双方撤回 / 真删"：我们没有对端 UI，且会**破坏 `talk/*.md` 权威源与审计**（`R-53` 已同判）；
- **误删可救**：界面给"**显示已删除**"开关（或 30 天回收站），台账侧**永不真删**；
- 面板与推送读数据时排除 `hidden_by_user=1`（推送不再因它响）。
**代价**：平台侧 `talk.py` 加一条写 op + 若干查询加 `COALESCE(hidden_by_user,0)=0`（**平台侧改动，需经理放行**）；App 侧一个长按菜单 + 一处过滤；**要重出包**；**不做**"撤回时限"这类复杂规则。
**判据（要能测）**：
1. 删完 App 列表行数 **-1**（读数）；`sqlite3 "select count(*) from msg"` **不减**（台账仍在）；
2. 重进页面/重启 App 后**仍不显示**（不是只在内存里过滤）；
3. 打开"显示已删除"能**找回**（读数与删除前一致）；
4. 推送不受影响：该条**不再触发** `notify`（`pushed_at` 不新增）；
5. `talk/*.md` 文本台账**字节数不变**（`ls -l` 前后对比）。

## 3. 一个聊天界面"该有什么功能"清单

**准绳**（我们自己的铁规，`docs/当前目标.md:14`、`docs/界面渲染规范.md:37,39`）：**界面不写说明文字 · 常驻按键 ≤3 · 一行一件事 · 一看就懂**；本条总目标（本人 2026-09-29）＝"**既兼顾简单易用，又兼顾它的专业性**"。

### 3.1 要（本版该有）

| 功能 | 为什么 | 代价 | 判据 |
|---|---|---|---|
| 发消息（单聊 / 频道广播） | 核心，已有 | 0（已交付） | 现有断言不回归 |
| 发送状态（两档小圈→对号）+ 失败红叹号可重发 | §1 结论 | talk.js+css，重出包 | §1.1/1.3 判据 |
| 删除我的历史 + "显示已删除" | §2 结论 | 平台加一列/一表 + App 菜单，重出包 | §2.2 判据 |
| 频道与单聊（点人说话、频道广播） | 已有（`R-42`/决定书 B 案） | 0 | 现有断言不回归 |
| 通知（收工 / 异常 / 长任务） | 已有（shell hook 推 QQ+手机） | 0 | 通知条数读数 |
| 会话抬头一行"与谁 / 哪个频道" | 已有（两行制信息行） | 0 | 抬头文本读数 |
| 时间戳 / 时间分隔 | Telegram、Signal 都有；我们有 per-bubble 时间 | 0（已有） | 时间字段非空 |
| **授权/收件人显式可见**（对应平台侧 `O-12`「授权者」角色） | 我们的特殊性：'这条发给哪个 session/谁回话' 需要看得见（本人 2026-09-27 已提 `O-12`） | 属平台侧（`roles-chat`），**不是 App 界面活**；App 只需**显示当前收件人**（已有输入条收件人条） | 抬头收件人与实际 `talk.say` 目标一致（台账核对） |

### 3.2 不要（明确不做，逐条给理由）

| 不做 | 理由（为什么对我们不合适） |
|---|---|
| **已读回执 / 双对号 / 蓝勾** | ① 数据源不存在（`msg` 表没有"已读"字段），做出来是**假信息**；② 我们对面是 agent，"已读"没有真实语义；③ 会增加"已读到哪一步"的沟通负担 |
| **对双方撤回 / 真删（服务端抹除）** | 会**破坏 `talk/*.md` 权威源与审计**（这是我们的台账，也是回放/追责的依据）；`R-53` 已同判 |
| **"正在输入…"** | 我们是异步、多角色在 tmux 里干活的模型，"正在输入"既不准也误导；且要多一条实时通道 |
| **语音 / 贴纸 / 表情包 / 红包式互动** | 与"整理与调度"的用途无关，纯增界面与审计负担 |
| **常驻"删除/清空"按钮** | 直接撞**常驻按键 ≤3** 铁规；删除是被动操作，只该在长按菜单里 |

### 3.3 以后再说（有基础、先不做）

| 功能 | 什么时候值得做 | 代价 | 判据（真做时） |
|---|---|---|---|
| 消息置顶/收藏 | 台账里出现"要反复看的决定"时 | 平台加一列 + App 一个标记 | 置顶条数读数 + 与台账一致 |
| 未读计数徽标 | 轮询已有基础，但会多一个常驻视觉元素 | App 侧计数（不新增按键） | 计数与 `notify` 未读一致 |
| 这段会话导出为 Markdown/文本 | 与"导出分享"同类，台账已存在（可直接给件） | 复用现成台账，代价小 | 导出文件与台账逐行一致 |
| 搜索历史（关键词） | 与社媒项目 `S-1` 的做法**同类**（`sqlite` 标准库即可，可复用） | App 加一个搜索入口（不能占常驻键，走长按菜单或抬头抽屉） | 必现词返回条数与 `sqlite3 count` **±0** |
| 免打扰 / 定时静音 | 与通知纪律相关（"与某人无关的事不要通知他"） | 平台侧通知规则 | 静音时段 0 条推送读数 |

## 4. 结论两句话（供他拍 `R-52`/`R-53`）

1. **发送状态**：**并进气泡那一行**（小圈→对号 两档，**不做已读/双勾**），**失败才出红叹号且可点重发**；成功态**不再**另起 `#tk-sends` 那条行 ⇒ 判据＝**气泡行高变化 0px**、成功态 `#tk-sends` 节点 0、三态各一次读数、点重发 `talk.say` +1 且气泡不增。
2. **删除历史**：**做"从我这儿删掉"（平台侧新列 `hidden_by_user` 标记隐藏 + App 长按菜单两档 + "显示已删除"可找回）**，**不复用** `hidden`（它是"隐形对接信息"语义）、**不做**对双方撤回/真删 ⇒ 判据＝App 行数 -1 而 `sqlite` 计数不减、重进仍在删、可找回、台账字节不变。

**查不到/未验的（照实说）**：① Signal 支持页两篇（`.../360007320751`、`.../360050426432`）**curl 403、浏览器也停在 Cloudflare 校验页** ⇒ 文里引的是搜索引擎回传的**该页原文摘要**，未逐字核；② **微信**"删除聊天记录只影响本端"**在官方帮助文档里查不到明确条目**（属公开可见行为）；③ **QQ 撤回 2 分钟**本轮没找到官方帮助页（只找到 QQ 机器人开发者文档里的"撤回消息"接口，`bot.q.qq.com/wiki/.../recall_message.html`，与客户端行为不是一回事）⇒ 标"未查证"。
