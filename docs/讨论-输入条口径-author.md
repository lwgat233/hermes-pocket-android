# ⑥讨论：输入条口径（R-41 / R-42 / R-44 是同一片输入区的三个症状）—— pipeline.author 的一份

> 讨论对象＝App 底部那条**常驻输入条**（`#composer`）。本人 2026-09-24 原话：「那个输入框一直保留在那里，就不太合理。如果你保留在那里，那按道理说……我可以使用它，把这段话发送给频道里的某个角色」。
> 我的角度＝**接线现状**：这条输入条的收件人是怎么定的、A 案要拔哪些分支、B 案要动哪些 `文件:行`。

## 一、现状：这条输入条的收件人是谁（不是角色，是"当前 tmux 窗口"）

- 控件＝`index.html:76-81`：`#composer`（`#cmode` 实时/攒着 ＋ `#cinput` textarea ＋ `#csend` ⏎）——**它就是"给 tmux 用的那条输入条"（R-44）**。
- 文字去向＝`app.js:1986-1994 sendLive(text)` → `this.send(text)`，**直接打进当前 attach 的 tmux 窗口**；实时模式下逐字送（`app.js:1898-1906`）。⇒ **收件人与屏幕上看的板/角色无关**，这就是"看着频道页、以为在跟角色说话、其实打进终端"的误会来源。
- 显隐是**全局**的：`app.js:2209`（`showComposer`/`showKeybar` 设置）＋ `app.js:624-640 fitChrome()`（可视高不够自动收起，`MIN_STAGE=110`）＋ `app.js:1442`/`1414`（抽屉「✎ 打开输入框」）＋ `style.css:561-562`（抽屉/沉浸联动）。
- **"发给某个角色"的能力其实早就有**：单聊页 `fire()` → `talk.js:1279 send(target, kind, body)` → 桥 `Bridge.kt:772 talk.say`；老路"切过去再打"也在（`talk.js:1374-1383`：`talk.switch` → `HP.App.send(cmd+'\r')`）。缺的只是**把底部那条输入条接到它上面**。
- 频道页现状（R-42 的现场）：频道页只有 3 个常驻键（`talk.js:483-509`：喊话 / ＋新对话 / 去群聊），**没有自己的输入入口** ⇒ "点开某人不能聊天"。
- R-41 刚落地（包 `unified-20260925-092803`，`app.js:14` feature 行）：回车发送已统一成一个函数 `talk.js:192-215 bindEnterSend(inp, fire)`（enterkeyhint + keyup/beforeinput 兜底 + 400ms 一把闸 + Shift/组字不发送）——**它是"每个输入框各自绑定、各自 fire"**，所以对 B 案**不冲突、可直接复用**。

## 二、候选 A（不该出现的场景就不保留输入条）的代价与风险

- 要拔/要加的分支（约 4-6 处）：`app.js:2209`（全局显隐）、`app.js:624-640 fitChrome`（自动收放）、`app.js:1442`＋`1414`（抽屉入口）、`style.css:561-562`（联动），外加一条"**哪些板算不该出现**"的白名单（`showBoard` 处要知道当前板）。
- 风险 1：**把本人明确要的能力一起砍掉**——他的原话是"我可以使用它，把这段话发送给频道里的某个角色"。
- 风险 2：**会复现"输入条/键条忽然消失"的老毛病**：`app.js:610-616` 的注释就是上一次"可视高不够→键条被挤出屏幕"的事故记录。A 案若与 `fitChrome` 各自为政，就会出现"时有时无"；必须规定**板级隐藏最后执行**。
- 风险 3：**隐藏输入条 ≠ 安全**：`#keybar` 功能键条还是常驻（同 `app.js:2209`），Ctrl/方向键照样打进当前 tmux 窗口（`app.js:1247-1249`），误打的窗口没变，只是少了一个看得见的输入框。
- 收益（A 最强的一点）：彻底消除"以为在跟角色说话"的误会，改动面最小。

## 三、候选 B（保留，但必须真能用：能指定发给频道里的某个角色）的代价与风险

- 要动的 `文件:行`（估计**约 30-60 行**，跨 3 个文件，不含 CSS）：
  1. `index.html:76-81`：给 `#composer` 加一行**收件人指示**（如 `#cwho`：「发给：#6 经理」/「发给：终端（roles:owner-me）」）；
  2. `app.js:1881-2000`（composer 段）：加**收件人状态 + 路由** —— 收件人＝角色时走 `talk.say`（复用 `talk.js:1279 send()` / `Bridge.kt:772`），收件人＝终端时保持 `HP.App.send`；
  3. `#cmode` 旁加**收件人切换**（或在会话页沿用"切过去"当终端模式入口）＝约 3-5 处新逻辑；
  4. `app.js:1904`（keydown）与 `1986-1994`（sendLive）两条 Enter 链**合并进 `bindEnterSend`**（talk.js:192-215），否则同一个控件两套判定 → 一次回车发两遍（`app.js:1904` 的 Enter 主路 与 `1922/1933/1958` 的实时直通分支并存，注释里记过"两边都接管＝一次回车发两遍（本地实测抓到过）"）；
  5. `talk.js` 里"点开某人 → 输入条收件人跟着变"（`openRole`/`openRoleSheet` 处同步，约 2 处）。
- 风险 1（最大）：**一个控件两种语义**。实时模式（`app.js:1976 liveInput()`）是"敲一个字就送进终端"，对角色收件人毫无意义（会把一句话拆成一堆单字消息）⇒ **实时模式与"收件人＝角色"必须互斥**，并在 UI 上看得出来（例如角色收件人时 `#cmode` 置灰并写「攒着」）。
- 风险 2：**误发对象**。收件人状态若只存内存、板切换/会话切换时没同步，就会出现"显示发给 A、实际发给 B"；必须规定**每次渲染从当前前台上下文推导**（不缓存）。
- 风险 3：**没有送达反馈**。`talk.say` 有 R-31/R-36 的状态行（`sends` 状态机），而终端输入条没有对应显示位 ⇒ 要么复用 `#tk-sends`，要么另加一行，否则"发出去了没"又变成黑箱。
- 风险 4：与 R-41 的**合并**成本（不合并＝一次回车发两条；合并＝要保证 400ms 闸在 composer 上仍然生效）。
- 收益：满足本人"能用它发给频道里的某个角色"的诉求，且**收件人显式可见**（不再靠"当前 tmux 窗口"隐式决定）。

## 四、我投哪一票

**投 B（保留输入条，但把它做成"收件人显式"的真输入条）。**
一句话理由：本人的重心是「要么能用、要么别摆」——A 把"能用"一起砍掉；B 只要把收件人做成**看得见的状态 + 明确的发送链路（talk.say）+ 与实时模式互斥**，就能同时满足"不误导"和"能用"。
（如果本人更想先要"不误导"，B 可以拆两步：先做收件人指示与路由，再谈实时模式。）
