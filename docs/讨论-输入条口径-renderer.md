# 讨论-输入条口径（renderer 的一份）

角色：pipeline.renderer（渲染者）· 2026-09-25 · 角度＝界面形态/渲染规范（谁渲染、在哪些页面出现、A/B 各要改哪些渲染面、重出包代价）
同一片输入区三个症状：**R-41**（回车不能确认/发送，已定位→实现→复测已派）、**R-42**（频道页点开不能聊天，待定位）、**R-44**（那条给 tmux 用的输入条在频道里也一直留着，本讨论）。

## 1) 候选 A（不该出现的场景就不保留输入条）——代价与风险
- **要动的渲染面**：`#composer` 是**全局元素**（`index.html:76`），它的显隐目前只由设置项管（`app.js:2209` 按 `showComposer` 整体显示/隐藏），**跟所在页面无关** —— 这就是"在频道里也一直留着"的直接原因。A 案＝把它的显隐升级成"按场景"：要在 board/栏目切换处同步显隐（`app.js` 一处主改）。**只需动 app.js 一个文件**（talk.js 不动）。
- **风险① 连带布局**：composer 与终端区共用底部空间，隐藏/显示要重算终端尺寸（`app.js:624-634` 的 `growComposer`/`maxHeight` + 终端 resize）。这条正是 `evidence/输入与发送栏/` 那几条读数（实时/去重/特殊键/中文上屏）覆盖的老坑 ⇒ 必须带一次 resize 去重与"切栏目不闪"的实测，不是改一行 CSS 那么简单。
- **风险② 误伤**：`.tk-askin` 这个类被 **5 处**复用（`talk.js:432`＋新角色表单、`:535` 群聊条、`:640` 授权回复框、`:937` 信息窗编辑态、`:1105` 单聊条）⇒ A 案若按类名或全局 CSS 隐藏，会顺手把授权框/新角色表单一起藏掉。**必须按 id（`#composer`）＋明确场景**做。
- **风险③ 少一条路**：隐藏后"想给 tmux 打字（中文/长文本）"要多一步（现在靠 `app.js:1414` 的「✎ 打开输入框」补），这条要留着，不能顺手删。
- **代价小结**：改动面**最小**（1 个文件、1 处显隐逻辑 + 1 条 resize 复验），不需要新增按键、不触碰铁规。
- **它不能解决的**：只是把"看起来能用"的假象去掉；"在频道里跟某个人说话"仍要靠 R-42 那条路。

## 2) 候选 B（保留，但必须真能用：能指定发给频道里的某个角色）——代价与风险
- **要动的渲染面**：`#composer` 现在的语义**只有一种**：写进 tmux 终端（`app.js:653` `session.write`）。B 案＝在同一个框里再加一种语义"发给频道里的某个角色"（走平台投递 `talk.say`）⇒ 必须让用户**一眼看出**这条会发到哪：要么加"收件人"常驻键、要么把收件人写进 placeholder/框体状态。
- **风险① 撞铁规**：`docs/界面渲染规范.md:37` **常驻按键 ≤3** —— 这条输入区现有"发送/收起"2 键，加一个收件人键就**到顶**，第 4 项必须收进"更多"；`同文件:39` **界面不写说明文字** ⇒ "终端注入 vs 频道投递"这种差别**不能靠一句话解释**，只能靠形态（图标/颜色/收件人条）自证。这两条一起把 B 案的摆法挤得很窄。
- **风险② 语义混装**：同一个框既是"给机器打字"又是"给人发消息"，用户按回车前不确定发到哪；发错（写进别人的 tmux / 广播给全体）比现在更糟 —— 与"一看就懂"直接冲突。
- **风险③ 改动面与重出包代价**：要动 `app.js`（分流 + 收件人形态）**和** `talk.js`（把 R-31/R-36 那套发送状态机：发送中/已送达+耗时/失败原因 接到这个框上，否则"发出去了"仍无反馈）⇒ **两个文件 + 一次合并重出包**，并按 R-31/R-36 的判据复测（送达读数、"假成功"三态）。比 A 案贵一档。
- **风险④ 能力重复**：B 想要的能力（发给指定角色）**已经存在**——单聊输入条 `talk.js:1095-1105`（`#tk-sayin`，收件人＝你点开的那个会话，走 `talk.say`）、群聊条 `talk.js:532-535`（广播）、授权框 `talk.js:638-640`（指定某条授权）。再让 `#composer` 也能"指定收件人"，等于**第二条通往同一目的地的路**，且这条路的入口本身是"终端"语义 —— 容易又长出一条"看起来一样、行为不一样"的通道。

## 3) 证据（可复核）
1. **`index.html:76`**（`<div id="composer" class="hidden">`，textarea `#cinput`）＋ **`app.js:2209`**（`$('composer').classList.toggle('hidden', !this.bool('showComposer', true))`）⇒ 这条是**全局元素、只按设置项显隐**，与页面无关 —— 复现本人在频道里看到它"一直在"。
2. **`talk.js:1095-1105`**（单聊 `#tk-sayline`，收件人＝打开的会话）／**`:532-535`**（群聊广播）／**`:638-640`**（授权框，指定某条授权）⇒ 三条**已有**输入条都已能"指定收件对象"；`#composer` 是唯一"发给机器"的那条（`app.js:653` `session.write`）。
3. **`docs/界面渲染规范.md:37` / `:39`**（常驻按键 ≤3；不写说明文字）⇒ B 案的"指定收件人"只有第 3 个常驻键位（到顶）或抽屉，且不许用文字解释两种投递差别。
4. **`talk.js:432 / 535 / 640 / 937 / 1105`**（`.tk-askin` 5 处复用）⇒ A 案隐藏必须按 id/场景，别按类名（否则连授权框一起藏）。
5. **既有读数**：`evidence/输入与发送栏/`（发送栏实时 / resize 去重 / 特殊键 / 中文上屏）⇒ 底部输入区与终端尺寸、输入法事件耦合，动它的显隐要连带复验布局。
6. **报告与登记**：R-41 定位 #1315 → 实现出包 **#1320**（`evidence/R41-实现与出包-20260925/`，三处 `enterkeyhint`、三路兜底、一次回车只一条）→ 复测 #1324 已派；登记表 R-42 行＝"待定位"、R-44 行＝"待定位（留档）"，本人口述原文在 R-44 行。

## 4) 我的票
**投 A**（不该出现的场景就不保留输入条）。
一句话理由：`#composer` 的语义是"写进 tmux 终端"（`app.js:653`），它放在频道页只会让人误以为能聊天；"发给频道里某个角色"这条路**已经由单聊输入条提供**（`talk.js:1095-1105`，收件人＝你点开的会话），所以 A 才是把假象去掉、又不新增第二条同义通道的做法 —— 代价也最小（只动 app.js 一处显隐 + 一次 resize 复验），而 B 要在同一个框里混装两种投递语义，直接撞"常驻键 ≤3 / 不写说明文字"两条铁规。
（附一句：A 案落地时若要更稳，可先只做"不在聊天栏目显示"这一档，并把"想给终端打字"的入口留在原处；R-42 修好前，频道页的人工对话仍应走"点人 → 单聊"。）
