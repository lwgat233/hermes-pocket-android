# 模块划分与实施顺序（Hermes Pocket 第二轮）

用户定的规矩：**架构规划和图形渲染优先于功能扩展；按模块修改、按模块打包、按模块测试。**
所以下面**不是按 log 的 1→12 顺序做**，而是把 12 条归到 4 个模块，先做承载一切的那个模块（界面/渲染），
每个模块**自成一轮**：改完 → 打一个包 → 只测本模块的功能点 → 归档。

## 为什么这么分（一个功能只属于一个模块）

| 模块 | 职责（一句话） | 覆盖条目 | 主要改动面 | 依赖 |
|---|---|---|---|---|
| **M1 渲染与界面架构** | 界面怎么长、怎么渲染、怎么不臃肿 | 1、7、9、11（界面侧） | `assets/ui/*`（JS/CSS/DOM） | 无（其它模块都往它上面挂） |
| **M2 会话与流程** | 连上之后走哪条路、状态是什么 | 6、10、12 | `assets/ui/app.js` + `Ssh.kt`/`Bridge.kt` | M1（会话面板要用统一行/抽屉） |
| **M3 Hermes 面板** | 远端 Hermes 的信息与操作 | 3、4、5 | `panels.js` + 原生 exec 通道 | M1、M2（状态与连接） |
| **M4 网络与流量** | 采集 → 统计 → 绘图（只此一处） | 2、8 | `app.js` 流量 + 新统计/绘图 + 原生（可选 ping 走 exec） | M1、M3（绘图复用行渲染/小窗） |

跨模块的只有**入口**（抽屉里一行跳过去），**控件不复制**。

## M1 渲染与界面架构（本轮先做）

目标：把「学来的 UI 渲染」（cdp 的那套，本目录 `界面渲染规范.md`）落到 Pocket，并把与渲染相关的老问题一起收掉。

- 顺序（一轮一个功能点，逐个验收）：
  1. ✅ **F-UI-9 字号/设置生效 + 回读**（uidx-A）
  2. ✅ **F-UI-1 长文本向下/一键到底/缓存上限**（uidx-B）
  3. ✅ **F-UI-7 左侧隐藏栏 + 功能登记表**（uidx-C：新增 `registry.js` / `ui.js`）
  4. ✅ **F-UI-11 启动加载时间线**（uidx-D：`HP.BOOT` 打点 + Hermes 页去重/缓存/短超时）—— M1 完成
- 打包：`gradle --no-daemon -Pkotlin.compiler.execution.strategy=in-process :app:assembleDebug`
  （容器 `notifbridge-emu` 内，镜像仓；**先停模拟器腾内存再构建**）。
- 测试：只测 M1 的 4 个功能点 + **回归「界面没被改坏」**（抽屉能开、4 个原有板块还能进、键条还在）。

## M2 会话与流程

目标：把「启动 → 挑 tmux → 进聊天 → 看得出状态」这条**流程**定下来并实装（这就是用户说的「使用根据流程」）。

- 顺序：1) ✅ **F-SESS-6** 启动挑 tmux（有就不动、没有才建、**永不 kill**）+ 会话清单/在线状态/选择（sess-A）；
  2) ✅ **F-SESS-12** 输出状态机（运行 / 压缩 / 结束 → 顶栏一行字 + 通知；规则表每条带依据与出处）（sess-B）；
  3) ✅ **F-SESS-10** 连接提示与「每次上传 key」的根因定位与修法（sess-C：提醒只放在真要人决定的分支）—— M2 完成
- 测试：假 SSH 服务器（`tools/tools-testssh2.mjs`）+ 真机模拟器里的真 `tmux`（模拟器里装 tmux 或用宿主容器内的 sshd）。
  判据读 `tmux ls` 与 `tmux display -p '#{session_name}'`，**PID 不变**才叫「没重建、没杀」。

## 每轮固定动作（照 `project-method-and-ui-doctrine` §3）

写目标（改 `当前目标.md`）→ 定数据（缺 op 先补 op）→ 接界面（一个渲染入口）→ **只测改动**（先证明跑的是新构件）→ 归档四样（哈希 / 证据 / 问题登记 / 覆盖自检）。
